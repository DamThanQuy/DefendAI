Mất kết nối giữa chừng — analysis phải làm lại từ đầu

Issue · DefendAI · chưa fix

1. Vấn đề

Kịch bản: User upload file → bắt đầu code scan / question generation → giữa chừng user mất mạng (tắt laptop, rớt WiFi, timeout proxy) → toàn bộ tiến trình phân tích đang chạy dở mất trắng.

Hiện tại cả POST /api/code/scan và POST /api/questions/generate đều xử lý đồng bộ trong HTTP request:

Client                          Server (FastAPI)
  │                                  │
  │── POST /api/code/scan ──────────→│
  │                                  ├─ get_doc() ← MinIO
  │                                  ├─ ZipFile.extract() ← RAM
  │                                  ├─ build_prompt()
  │                                  ├─ ai_gateway.generate() ← 3-10s
  │         [MẤT MẠNG]              ├─ normalize result
  │✗─────────────────────────────→  │✗ response không về được
  │                                  │
  │── POST /api/code/scan ──────────→│  ← phải làm LẠI TỪ ĐẦU
  │                                  ├─ get_doc() ← lại MinIO
  │                                  ├─ ZipFile.extract() ← lại
  │                                  ├─ build_prompt() ← lại
  │                                  ├─ ai_gateway.generate() ← lại
  │                                  └─ OK (lần này may ra không mất mạng)

4. Hướng giải quyết (đề xuất)

Cách 1 — Async Job Queue (khuyên dùng)

BướcMô tả
1POST trả về ngay 202 Accepted + job_id
2Background worker (Celery / ARQ / BackgroundTasks) nhận job, chạy analysis
3FE polling GET /api/jobs/{id} để lấy kết quả khi xong
4Mất mạng → chỉ mất polling request, job vẫn chạy trên server

ponytail: Cần Redis/Celery. Nếu không muốn thêm infra, dùng BackgroundTasks của FastAPI + polling từ DB (đơn giản hơn).

Cách 2 — Cache partial result + resume

BướcMô tả
1Trước khi gọi AI, lưu analysis.status = processing
2Nếu user re-call với cùng document_id, check status == processing → chờ (poll / websocket)
3Nếu server crash → status chuyển về failed sau TTL, user retry

ponytail: Chỉ tránh được repeat khi request timeout giữa chừng, không xử lý được server crash.

Cách 3 — FastAPI BackgroundTasks (nhẹ nhất, không thêm infra)

BướcMô tả
1Route trả về 202 ngay, schedule analysis qua BackgroundTasks
2Worker lưu kết quả vào DB khi xong
3FE poll kết quả

ponytail: BackgroundTasks chạy cùng process, không scale được. Nếu server restart là mất job đang chạy.
